## Context

This is Milestone 2 of an assignment. Its learning objectives are document chunking and embedding, vector databases, retrieval pipelines and semantic search.

- **Part A (50%), `resume_rag.py`**:
  - Load resumes with the Milestone 1 file-system tools.
  - Chunk them by section (Education, Experience and so on).
  - Embed the chunks and store them in a vector DB.
  - Extract Name, Skills, Experience Years and Education as metadata for filtering.
- **Part B (50%), `job_matcher.py`**:
  - Accept a job description and embed it.
  - Retrieve the top 10 resumes with **hybrid search** (semantic + keyword for critical skills).
  - Score each match 0–100, explain which sections matched, and filter on must-have requirements (e.g. "5+ years Python").
- **Deliverables**:
  - The complete RAG implementation.
  - At least 30 diverse resumes and 5 job descriptions.
  - A Jupyter notebook with experiments and analysis.
  - Performance metrics (retrieval accuracy and latency).
  - A 3–4 minute demo video.

**Required output format** (extra fields are allowed and listed in Step 4):

```json
{
  "job_description": "...",
  "top_matches": [
    {
      "candidate_name": "John Doe",
      "resume_path": "resumes/john_doe.pdf",
      "match_score": 92,
      "matched_skills": ["Python", "Machine Learning"],
      "relevant_excerpts": ["..."],
      "reasoning": "Strong match for ML experience..."
    }
  ]
}
```

## Key decisions

| Decision | Choice | Why |
|---|---|---|
| Reusing Milestone 1 (M1) | **Git submodule** at `vendor/file-system-assistant` | Reuses M1 visibly without duplicating code |
| Embeddings | **HuggingFace sentence-transformers, run locally** | Free, no API key or rate limits, reproducible metrics |
| Vector DB | **ChromaDB** (local `PersistentClient`) | Embedded, no server; supports array metadata filters |
| Metadata and reasoning | **Rule-based**, with an optional Gemini `--llm` flag | Deterministic and testable; the LLM is an optional extra for prose |
| Dataset | **Synthetic, generated by a script**, with ground-truth labels | Gives measurable retrieval accuracy |

## Research findings that shaped the design

- **ChromaDB 1.5.x** has supported **array metadata** since Feb 2026 ([changelog](https://www.trychroma.com/changelog/metadata-arrays)). All elements must share one type, and filters use `{"skills": {"$contains": "python"}}`. Combined with `$gte` and `$and` ([where-filter reference](https://docs.trychroma.com/reference/where-filter)), this means skills and experience filters run **inside the vector DB**.
  - Set the distance metric with `configuration={"hnsw": {"space": "cosine"}}` ([configure docs](https://docs.trychroma.com/docs/collections/configure)). `metadata={"hnsw:space": ...}` is legacy.
  - Pass precomputed embeddings and set `embedding_function=None`, so Chroma never downloads its default ONNX model.
- **Chroma's native BM25/sparse hybrid search only works on Chroma Cloud** ([sparse vector search](https://trychroma.com/project/sparse-vector-search)). With a local `PersistentClient`, the standard pattern is a separate BM25 index whose results are merged in our code with **Reciprocal Rank Fusion (RRF)**.
- **rank-bm25** is tiny and fine for 36 documents. [`bm25s`](https://bm25s.github.io) is faster but heavier, which doesn't matter at this scale.
- **sentence-transformers 6.x** supports Python 3.10–3.14 ([PyPI](https://pypi.org/project/sentence-transformers/)). On Linux, plain `pip install torch` pulls in CUDA wheels worth gigabytes, so **CI installs torch from `https://download.pytorch.org/whl/cpu`**.
- **Embedding candidates** for the experiments:
  - `BAAI/bge-small-en-v1.5` (33M parameters, 384 dims, query prefix `"Represent this sentence for searching relevant passages: "`) is the **default**.
  - `sentence-transformers/all-MiniLM-L6-v2` (22M parameters) is the baseline.
  - `Qwen/Qwen3-Embedding-0.6B` (1024 dims, query via `prompt_name="query"`) is the quality ceiling, used for the accuracy-vs-latency trade-off.
- **Retrieve-then-rerank** with a cross-encoder is common in job matching. Published gains are small when the hybrid first stage is already strong ([arXiv 2605.27656](https://arxiv.org/pdf/2605.27656), [arXiv 2609.23307](https://arxiv.org/pdf/2609.23307)). Reranking is therefore an **optional stage plus one experiment**, not the default.
- **Label quality drives the evaluation.** Ground truth taken from generator metadata can inflate scores, so the dataset deliberately includes paraphrased skills, skills that appear only in bullets, and hard negatives. The notebook states plainly that the labels are synthetic.
- **M1 constraints**:
  - `read_file` truncates text at 20k chars, which is fine for resumes.
  - The submodule URL must be **https** so public cloners need no SSH keys.
  - pypdf extraction can reflow lines, so Step 2 round-trips every generated PDF through M1 `read_file` and the section detector.

## Step 3: Part A (`resume_rag.py`)

1. **Load**: call `list_files` for each supported extension, then `read_file` for each file. Report failures and empty-text warnings, and skip those files.
2. **Section detection**:
   - A header is a short line (5 words or fewer) that matches a synonym map after normalising case and stripping a trailing `:`. The canonical sections are summary/profile/objective, experience/employment/work history, education, skills/technical skills/core competencies, projects and certifications.
   - Also handle inline headers such as `Skills: Python, SQL`.
   - Text before the first header becomes the `contact` section.
3. **Chunking** (`chunk_strategy`: `section` is the default; `fixed` and `whole` are for Experiment A):
   - Make one chunk per section.
   - Split Experience **per job entry**: a line containing a date range starts a new entry.
   - If a chunk is still over about 1,000 chars, split it at bullet boundaries with a one-bullet overlap. bge-small accepts at most 512 tokens.
   - Prefix each chunk's embedded text with `"{name} | {section}\n"` for context.
   - Chunk ids look like `{candidate_id}::{section}::{n}`.
   - `fixed` uses 500-char windows with 100 chars of overlap. `whole` embeds the entire resume as one chunk.
4. **Metadata extraction** (`extract_metadata(...) -> CandidateProfile` dataclass):

   | Field | How it's extracted |
   |---|---|
   | name | First contact line with 2–4 capitalised words and no digits, `@`, `\|` or `http`; falls back to the filename |
   | email, phone | Regex |
   | skills | Taxonomy aliases matched on word boundaries; records which sections each skill appears in |
   | experience_years | An explicit "N+ years" wins. Otherwise parse the date ranges in Experience, merge overlapping intervals and sum them ("Present" means today) |
   | skill_years | For each skill, the merged duration of the job entries that mention it (drives "5+ years Python") |
   | education | Highest degree (PhD 4 / Master 3 / Bachelor 2 / Associate 1), plus field and institution where detectable |

5. **Embed and store**:
   - `get_embedder(name)` wraps SentenceTransformer, using `normalize_embeddings=True`, batching, and the per-model query prompt from `config`. Tests inject a fake embedder instead.
   - Store in ChromaDB `PersistentClient("index/chroma")`, one collection per (model, chunking) pair, e.g. `resumes__bge-small__section`, so experiments don't collide. Create each collection with `configuration={"hnsw": {"space": "cosine"}}` and `embedding_function=None`.
   - Chunk metadata: `candidate_id`, `name`, `resume_path`, `section`, `experience_years` (float), `education_level` (int), `skills` (string[]).
   - Save full profiles (including skill_years and chunk texts) to `index/<collection>/candidates.json`. BM25 and the reasoning step read them from there.
   - Ingest is **idempotent**: it deletes and recreates the collection on every run.
6. **CLI**:

   ```bash
   python resume_rag.py ingest [--model bge-small] [--chunking section]
   python resume_rag.py stats
   ```

   `stats` prints chunk counts per section, a table of extracted profiles, and ingest timings.

**Deviation:** Part A was split from a single `resume_rag.py` into the eight small, single-concern modules listed in [Target repo layout](#target-repo-layout) (`resume_loading.py`, `resume_sections.py`, `resume_chunking.py`, `resume_dates.py`, `resume_metadata.py`, `resume_embedding.py`, `resume_storage.py`, `resume_models.py`), for readability. `resume_rag.py` now only wires up the `ingest`/`stats` CLI. Behaviour is unchanged: re-verified the same 36/36 load, 236-chunk ingest, and 100%/94% name/years accuracy after the split.

**Deviation:** a date range with only a bare year (the `short_dash` style, e.g. `"2022-2023"`) loses sub-year precision. Parsing it as January 1st biased `experience_years` low; combined with "Present" resolving to the real `date.today()` (months ahead of the dataset generator's fixed `TODAY`), two candidates' computed years drifted far enough to miss the ground truth by more than a year. Bare years now parse to July 2nd (the unbiased midpoint), and a same-day/overlapping range is padded by 182 days instead of snapping to December 31st. This raised years-within-±1-year accuracy from 86% to 94% (36/36 names match exactly). The residual two mismatches are themselves a dataset property: `date.today()` keeps moving further from the generator's fixed reference date, so this gap will widen over time — a candidate for Step 5's "threats to validity" writeup, not something Step 3 should special-case away.

## Step 4: Part B (`job_matcher.py`)

1. **JD parsing**:
   - Take the title from the first line.
   - Find the Requirements/Must-have and Nice-to-have blocks using header synonyms.
   - Taxonomy matching gives `required_skills` and `preferred_skills`.
   - Extract must-haves with regex:
     - `(\d+)\+?\s*years?[^.\n]{0,40}?<skill>` sets a per-skill minimum.
     - A bare "N+ years of (professional) experience" sets a minimum on total years.
     - Degree words set a minimum degree level.
   - `--must-have "5+ years Python"` (repeatable) adds to or overrides these.
2. **Semantic retrieval**:
   - Embed the JD with the model's query prompt.
   - Run `collection.query(query_embeddings=..., n_results=50, where=prefilter)`. The **prefilter** covers the must-haves Chroma can express: `skills $contains` for each must-have skill, `experience_years $gte` and `education_level $gte`.
   - Group the returned chunks by candidate. A candidate's semantic score is `0.7·max + 0.3·mean(top-3)` cosine similarity. Keep the best similarity per section for the reasoning step.
3. **Keyword retrieval**:
   - Run BM25Okapi over each candidate's full text.
   - Tokenise with lowercasing and alias normalisation from `skills.py`, so "k8s" counts as "kubernetes".
   - Separately, **critical-skill coverage** is the share of `required_skills` found in the profile.
4. **Hybrid fusion**: merge the semantic and BM25 rankings with **RRF** (k=60) to form the candidate pool. This keeps a strong keyword match even when its embedding scores lower.
5. **Post-filter**:
   - Check per-skill years (`skill_years[s] >= min`), which Chroma's filters can't express.
   - Run this **before** the top-K cut, so all K results are eligible.
   - Rejected candidates go into `filtered_out` with their reasons, e.g. `"Python: 3.0 yrs < 5 required"`.
   - `--soft` keeps them in the ranking with a −20 penalty instead.
6. **Optional rerank** (`--rerank`): `cross-encoder/ms-marco-MiniLM-L6-v2` scores (JD, best chunks) pairs for the top 20, and its score replaces the semantic component.
7. **Score** (an int from 0 to 100):

   ```
   score = 100 · (0.50·semantic_cal + 0.20·bm25_norm + 0.25·required_cov + 0.05·preferred_cov)
   ```

   - `semantic_cal` maps cosine linearly from [lo, hi] to [0, 1], clipped. The bounds are fixed per model in `config`, so scores are comparable across JDs. They get tuned in the notebook.
   - `bm25_norm` is the BM25 score divided by the pool's maximum.
   - The weights live in `config.py`.
8. **Evidence**:
   - `matched_skills` is the profile's skills that appear in the JD's required or preferred lists, with required skills listed first.
   - `relevant_excerpts` holds the top 2 chunks by similarity (trimmed to about 300 chars), plus M1 `search_in_file` snippets for up to 2 matched required skills.
   - The template reasoning includes:
     - A band: Strong ≥ 80, Good ≥ 60, otherwise Partial.
     - The closest sections, with their similarities.
     - Required-skill coverage, naming any missing skills.
     - The must-have result.
   - `--llm` sends **only this structured evidence** to Gemini (`GEMINI_MODEL`, using the same client pattern as M1's `make_client`) for a two-sentence summary. It falls back to the template on any error.
9. **Output**: exactly the required format, with `resume_path` repo-relative. It also adds `score_breakdown`, `section_scores`, `must_have_check`, `filtered_out` and `latency_ms`. The result is written via M1 `write_file` to `outputs/matches/<jd>.json` and printed to stdout.
10. **CLI**:

    ```bash
    python job_matcher.py --jd <file> | --text "..." | --all \
        [--k 10] [--must-have "5+ years Python"] [--soft] [--rerank] [--llm] [--mode hybrid|semantic|keyword]
    ```

**Deviation:** Part B was split into the six single-concern modules listed in [Target repo layout](#target-repo-layout) (`match_models.py`, `jd_parsing.py`, `retrieval.py`, `match_filtering.py`, `match_scoring.py`, `match_evidence.py`), for the same readability reason as Step 3's split. `job_matcher.py` only wires them together and owns the CLI. Agreed with the user before building, since it's a bigger structural change than the plan's single-file layout.

**Deviation:** the per-skill-years regex (`(\d+)\+?\s*years?[^.\n]{0,40}?<skill>`) matches every skill named in its 40-char window independently, which breaks on lines like "3+ years of experience with TensorFlow or PyTorch": both skills got an **independent** minimum, so a candidate strong in one but not the other was wrongly disqualified. `jd_parsing.py` now also returns `skill_year_alternatives` (OR-groups) whenever matched skills on the same line share a figure and the line contains "or"; `match_filtering.py` passes a group if *any one* skill meets the minimum, and `retrieval.py`'s Chroma prefilter mirrors this with `$or`. Skills joined by "and" are unaffected (still an AND, one minimum each).

**Deviation:** `resume_metadata.py`'s `skill_years` (Step 3) only credited years to a skill found by name inside a dated experience entry. In practice most resumes name specific frameworks in bullets ("FastAPI", "Django", "PostgreSQL") without repeating the base skill ("Python") there — it only appears on the Skills line. ## Step 5: Metrics (`evaluate.py`)

  ```
  skill_years[s] = max(
      evidence_years(s),   # merged duration of dated experience entries that name s
      claimed_years(s),    # skill-specific claim in Summary, e.g. "6 years of Python"
      listed_years(s),     # experience_years if s appears in the Skills or Summary section, else 0
  ```

  - **Why this shape:** a monotonic policy must give "listed, but in no dated entry" a value no larger than any evidence-backed value. Today that case gets total years while one bullet in a short job lowers it (R7).

    - A skill that appears only in bullets still gets its evidence-based years, so per-skill specificity survives.
    - Taking the max means more evidence can only raise the value.
    - The filter stays strict (see Decisions), so false negatives are the costly error: a qualified candidate silently dropped. This policy is the one that removes them.
  - **Measured on the current dataset** (prototype against today's `jd_parsing.py`, before Step 8; must-have verdicts for 36 resumes × 6 JDs, extracted vs. true values):

    | Current (dated evidence, else total) | 48 | 93.5% | 10 | 4 | 63.4% |
    | Total years for every found skill | 0 | 93.5% | 14 | 0 | 61.6% |
    | Evidence + claims only, no fallback | 0 | 93.1% | 4 | 11 | 49.5% |
    | **Chosen: evidence, claims, total if listed** | **0** | **95.8%** | **9** | **0** | 62.5% |

## Step 11: One ranking pipeline

Branch `step-11-single-ranking-pipeline`. Fixes A1–A3 (the per-query parts), A6, A7, R19–R21. **Design approved by the user on 2026-10-30.** It changes ranking semantics, so every caller, notebook, test and doc must be brought in line in this step (see the conformance sweep). [Step 11 verification](#step-11-verification) then confirms it in a separate session.

**The approved pipeline**, the only ranking path in the repo:

```
parse JD → candidate generation → must-have filter → score → (optional) rerank → sort → top-K
            union(top N_SEMANTIC by semantic, top N_BM25 by BM25), ordered by RRF
```

- **A1:**
  - A single `rank(jd, index, options) -> Ranking` (new module `ranking.py`). It returns the ordered candidates with score breakdowns, filter results, semantic hits, RRF scores and per-stage timings.
  - It is the **only** caller of `semantic_search`, `bm25_search`, `rrf_fuse`, `filter_candidates`, `score_candidate` and `rerank_semantic`.
  - `job_matcher.match_jd` adds evidence and output on top; `eval_ranking.py` (or `evaluate.py` directly) and `notebooks/_setup.py` call `rank()`. Delete `eval_ranking.rank_candidates`' and `_setup.score_all`'s copies of the pipeline.
- **A2, candidate generation:**
  - The pool is the union of the top-`N_SEMANTIC` candidates by semantic score and the top-`N_BM25` by BM25 (both sizes in `config.py`).
  - **RRF orders the pool** and is the **tie-breaker** after score (then name), so `config.RRF_K` has an effect with or without rerank.
  - Only pool candidates are filtered and scored; anyone outside the pool isn't ranked.
  - The must-have filter still runs on the whole pool **before** the top-K cut (AGENTS.md hard rule).
  - Hard mode applies the Chroma prefilter; soft mode doesn't (Step 10's R1 fix carries over).
- **R21:** compute semantic similarity for **every** pool candidate, including BM25-only ones, with a second Chroma query restricted by `candidate_id $in [...]`. Missing candidates no longer default to 0.
- **R19, rerank on one scale:**
  - With `--rerank`, the cross-encoder scores **every candidate in the filtered pool**, not just the top 20.
  - Its raw score is mapped to [0, 1] with fixed per-model bounds in `config.py` (the same `calibrate()` as cosine) and replaces the semantic component for all of them. One scale per sort, always.
  - Query it with a condensed JD (title + requirement lines) rather than the whole text.
  - Cross-encoder model id, revision and calibration bounds go in `config.py`.
  - Remove the hard-coded rerank pool of 20.
- **R20:** normalise BM25 against a fixed, per-JD reference, e.g. the BM25 score of the JD's own requirement text, so scores are comparable across JDs. Document the choice in `config.py`.
- **A3 (per-query parts):** load candidates once per process, not per call. Build excerpts from stored chunk text plus an in-memory alias-aware keyword search, so PDFs aren't re-parsed per query. This replaces Step 4's per-query `search_in_file` call (M1 stays the only loader); record that as a deviation.
- **A6:** `evaluate.py` and the notebooks ingest into a separate index directory (`config.EVAL_INDEX_DIR`), never the one `job_matcher.py` serves.
- **A7:** move every remaining tunable into `config.py`.
- **Conformance sweep:** in the same PR, update everything that describes or depends on the old pipeline:
  - **Code:** `job_matcher.py`, `evaluate.py`, `eval_ranking.py`, `notebooks/_setup.py`, and the module docstrings of `retrieval.py` and `match_scoring.py` (both describe the old prefilter and top-N rerank).
  - **Notebooks:**
    - `03_experiment_b_search_mode`: what keyword-only and semantic-only mean for pool generation.
    - `05_experiment_d_weights_and_rrf`: RRF now matters without rerank, so sweep `RRF_K` with rerank off too, and replace the old "RRF only affects rerank" finding.
    - `06_experiment_e_rerank`: rerank over the whole filtered pool.
    - `07_calibration_and_analysis`: conclusions.
  - **Tests:** e2e, retrieval and scoring tests updated; new tests for pool generation, RRF tie-breaking and the single rerank scale.
  - **Docs:** README (mermaid diagram, design-decisions table, the `--rerank` description "top 20", metrics); PLAN Step 4 items 2, 4, 5, 6 and 7 and Step 6's Experiment D deviation, each marked *superseded by Step 11* with a one-line pointer; AGENTS.md's Project description if any of it is no longer accurate.
  - **Outputs:** regenerated `outputs/matches/*.json` and `outputs/metrics.json`.

- **A4, safe full rebuild:** ingest builds into a new, build-id-suffixed Chroma collection and a new `candidates.json`, written via temp file and rename.
  - Only after both succeed does it atomically replace a small pointer file in the collection's index directory naming the active collection and build id. Then it deletes the previous build.

It removes the candidate's chunks from Chroma (`where={"candidate_id": …}`) and their profile from `candidates.json` (atomic rewrite), and records the deletion in `ingest_stats.json`. Encryption at rest is a deployment concern, covered by Step 16's privacy doc (encrypted volume).
